# MV-DUSt3R 优化研究报告

文档日期：2026-04-01  
研究范围：基于当前工作区已落地代码，对 Phase 1 与 Phase 2 的工程设计、实现路径、收益预期、验证现状和后续工作进行系统梳理  
文档语言：中文

## 摘要

本轮工作试图同时解决两个实际工程问题：

1. 多视图重建推理过程在显存和算力上成本偏高，尤其在 12GB 级别单卡条件下，现有路径缺少稳定的低显存运行策略。
2. 当输入图像质量较低，或者训练中的几何监督本身存在噪声时，模型对输入退化和标签退化的鲁棒性不足，容易导致重建质量不稳定。

为此，本轮改动采用了“双路径”策略：

- Phase 1 处理推理期问题，强调低显存和输入稳健性。
- Phase 2 处理训练期问题，强调 corruption-aware 训练与 noisy geometry 下的损失重加权。

本轮工作没有引入新的 student 模型或蒸馏路径，因此整体策略是“先用运行时优化和训练策略优化解决问题，再决定是否需要结构性压缩”。

## 1. 问题背景

从工程角度看，原始链路存在以下典型矛盾：

### 1.1 推理显存与算力成本高

多视图重建天然存在两个昂贵部分：

- pairwise 前向数量随视角关系图增加
- global alignment 常采用固定迭代数，存在明显无效优化尾部

这意味着，即便模型本体不变，推理成本仍可能远高于单次前向本身。

### 1.2 输入图像质量下降时，置信度阈值容易误伤

在低对比度、轻度模糊、噪声较多或曝光异常的图像上，固定阈值往往会出现两个极端：

- 过度裁点，导致可用于焦距估计、位姿校准和点云融合的有效点数不够
- 过度保留，导致低质量区域引入更多错误几何

因此，阈值不应只由一个固定百分位控制。

### 1.3 训练 supervision 本身可能带噪

多视图训练数据常见问题包括：

- depth 稀疏或局部错误
- pose 略有偏差
- focal 不稳定

如果仍用干净样本同样的权重强行拟合，会把模型朝错误监督方向推。

## 2. 目标定义

本轮工程目标不是“从头重做模型”，而是建立一个可演进的稳健化基座。

### 2.1 Phase 1 目标

- 降低推理链路显存占用
- 减少不必要的 GO 迭代
- 在低质量输入下尽量避免阈值坍塌
- 保持现有模型权重与输出接口兼容

### 2.2 Phase 2 目标

- 让训练链路理解样本何时是 clean、何时是 RGB degraded、何时是 geometry corrupted
- 对 geometry-corrupted 样本降低对 GT geometry 的依赖
- 保持渲染一致性和多视图一致性信号不被同步削弱

## 3. 设计原则

本轮实现遵循了四个原则。

### 3.1 尽量不改模型结构

原因很直接：

- 结构改动会牵涉 checkpoint 兼容、训练稳定性、推理部署、实验对照等多个面
- 目前更大的瓶颈来自工程链路，而非模型定义本身

因此，本轮优先选择：

- 运行时调度
- 输入预处理
- 数据增强
- loss 重加权

### 3.2 优先可插拔，而不是全面替换

这体现在多个地方：

- 新增 `runtime_profile`，保留默认路径
- 新增 robust 训练脚本，不覆盖原脚本
- 新增 corruption helper，而不是把逻辑散落在 dataset / loss / demo 各处

### 3.3 对 noisy geometry 只下调 GT 拟合项

如果一个样本的几何真值被故意注入噪声，那么正确做法不是整体降低这个样本的所有 loss，而是只降低依赖几何真值的部分。

因此，本轮将：

- `Regr3D`
- `GSRenderLoss` 中依赖 GT geometry 的 local / lap 项

做了权重下调，而没有同步削弱 RGB 重建和 render consistency 主路径。

### 3.4 在低质量输入上保底，而不是极端筛选

原始固定 3% cutoff 的问题在于，它默认认为每张图都有足够质量支撑 percentile 筛点。  
现实并非如此。

因此本轮改成：

- 百分位阈值仍保留
- 但增加 `min_keep` 下界，避免有效点集被完全裁空

## 4. Phase 1 技术路线

## 4.1 低显存推理

核心手段有两个：

### AMP

通过 `autocast` 减少激活和中间张量开销。  
它不是普适加速银弹，但在大多数推理路径上都能以较低改动成本换来可观显存收益。

### OOM 递减回退

在 pairwise 推理阶段，一旦初始 batch size 过大，系统现在会自动尝试更小的 batch，而不是直接异常退出。  
这使运行时从“单点失败”变成“代价退化但可完成”。

工程意义：

- 它比人工多次试参更适合容器化和远程部署
- 对 batch shape 相对统一的输入效果尤其明显

## 4.2 输入预处理与质量感知

图像质量评分用于估计输入是否存在：

- 模糊
- 对比度不足
- 曝光裁切

在此基础上：

- 低质量图像可启用轻量去噪
- 可做亮度归一化
- 在极低质量条件下做轻度锐化
- 阈值侧则根据图像质量动态调整裁点激进程度

研究判断：

- 这一策略本质上不是替代模型鲁棒性，而是在模型前加一个轻量防护层
- 它的成本远低于重新训练一套“低光鲁棒版本模型”

## 4.3 Scene Graph 优化

在视角数不大时，完整图最简单直接。  
但一旦视角数增长，完整图会带来明显的 pair 数膨胀。

引入 `anchorlocal` 的原因：

- anchor 提供全局联通性
- local edges 保留邻域几何约束
- 比完整图更省 pair 数
- 比纯局部滑窗更稳

这里使用图像质量分数自动选 anchor，是一个工程启发式：

- 高质量图更可能提供更稳定的全局参照
- 不需要引入更复杂的先验模型

## 4.4 GO 早停

GO 原先固定迭代的主要问题不是“会不会收敛”，而是“经常在已经收敛后继续烧算力”。

本轮做法：

- 设置最小迭代数，防止过早停止
- 设定检查周期，降低判断抖动
- 用相对改善度作为准则，而不是绝对 loss
- 用 `patience` 吸收短期震荡

研究判断：

- 这是一种典型工程折中，不追求理论最优停止点，而追求高概率减少尾部浪费

## 5. Phase 2 技术路线

## 5.1 为什么需要三类样本

本轮 corruption-aware 训练不是只加“脏图像”，而是将样本分为三类：

- clean
- RGB-corrupted
- geometry-corrupted

原因在于，这三类样本对训练的含义不同：

- clean 样本提供基准监督
- RGB-corrupted 样本测试模型对输入退化的稳健性
- geometry-corrupted 样本测试训练是否会被错误几何标签拖偏

若把后两类混在一起但使用统一 loss 规则，训练信号会失真。

## 5.2 为什么 corruption 决策要按 sample 统一

如果每个视角都独立随机做不同强度扰动，会出现两个问题：

- 多视图之间统计分布差异过大
- 模型学到的不是稳健重建，而是混乱对齐

因此本轮使用“按 datapoint 统一采样 corruption state”的方式：

- 整个样本统一为 clean / rgb / geometry 之一
- 各视图共享这一模式

这使 Phase 2 更像“场景级扰动训练”，而不是“单张图随机增强训练”。

## 5.3 几何噪声为何只降低 GT geometry loss

如果 geometry corruption 被注入到了：

- depth
- intrinsics
- pose

那么依赖这些真值构造出的 `pts3d` 本身就不再是可靠监督。  
此时继续用原权重逼迫模型去拟合，等同于把错误监督当金标准。

因此采用如下策略：

- 几何真值驱动的 loss 降权
- RGB / LPIPS / render consistency 维持原强度

这一策略的本质，是把训练从“强监督拟合错误标签”改为“弱监督容忍错误标签，同时保留可验证的一致性目标”。

## 5.4 为什么保留 render consistency 的权重

render consistency 的价值在于：

- 它约束的是生成结果与观测图像之间的对应关系
- 它比被主动扰动过的 geometry GT 更接近真实观测

如果 geometry noise 样本里把 render consistency 也一起降权，会导致这类样本几乎失去训练价值。  
因此本轮只下调几何拟合项，不下调渲染主项。

## 5.5 置信度裁点的保底策略

低质量输入条件下，固定 percentile 有时会保留太少点，带来连锁问题：

- 焦距估计失稳
- PnP 位姿估计失稳
- GO 初始化点不足

因此增加最小保留点数是必要的。  
这不是为了提高理论精度，而是为了避免系统在边缘样本上失去基本可运行性。

## 6. 代码路径与数据流变化

## 6.1 推理路径

新推理路径可以概括为：

1. `load_images()` 载入图像
2. 计算图像质量分数
3. 按 `preprocess_profile` 执行预处理
4. 在 `demo.py` / `inference_global_optimization.py` 中根据质量调整阈值
5. `inference.py` 负责 AMP 与 OOM fallback
6. `image_pairs.py` 负责 `anchorlocal` 等 scene graph
7. `base_opt.py` 负责 GO 早停

## 6.2 训练路径

新训练路径可以概括为：

1. `MVDataset` 采样 datapoint
2. `build_corruption_state()` 决定样本模式
3. 执行 RGB corruption 或 geometry corruption
4. 在每个 view 中写入 corruption metadata
5. `losses.py` 读取 `geometry_loss_weight`
6. `Regr3D` 和 `GSRenderLoss` 对 noisy geometry 样本做降权

## 7. 验证现状

## 7.1 已完成验证

已完成的验证只有静态层：

- `python -m py_compile` 成功通过

其意义是：

- 当前修改在 Python 语法上是自洽的
- 各模块的 import 链未出现直接语法性破坏

## 7.2 尚未完成验证

以下验证还没有完成：

- Docker 实际 build
- demo / CLI 推理的端到端 GPU smoke test
- 12GB 显存条件下的真实峰值显存与延迟测量
- robust fine-tune 的训练收敛验证
- clean set / degraded set 指标回归

## 7.3 环境限制

在当前 shell 环境里执行额外 Python smoke test 时，发现 `python` 缺少 `numpy`。  
这表明当前命令环境不能代表真实训练运行时，因此：

- 本地小测试失败不能说明代码逻辑错误
- 也不能把当前环境视为训练或部署环境的有效替代

## 8. 风险分析

## 8.1 Phase 1 风险

- AMP 可能在极个别路径引入数值差异
- `anchorlocal` 是启发式策略，并非所有数据集都优于完整图
- GO 早停的阈值仍需在真实 benchmark 上校准

## 8.2 Phase 2 风险

- corruption 强度与概率目前是经验值
- geometry noise 下的 0.3 权重并无实验最优性保证
- 如果数据本身 already noisy，再叠加人工噪声，可能需要更温和策略

## 8.3 工程风险

- 训练脚本默认依赖固定输出目录命名
- 真实多机多卡训练尚未验证
- Docker 中 RoPE CUDA kernel 与 PyTorch3D 编译需要真实环境确认

## 9. 未实现但应关注的方向

虽然用户要求推进 Phase 2，但从完整路线图看，仍有一些方向没有实现：

### 9.1 Student 模型压缩

如果仅靠 AMP、OOM fallback、scene graph 优化和 GO 早停仍无法满足目标延迟，那么下一步最可能需要的是结构性压缩，而不是继续堆运行时技巧。

### 9.2 Teacher-Student 蒸馏

当前 robust fine-tune 仍完全依赖 GT / render consistency。  
若需要进一步压缩模型，同时保持 clean set 表现，蒸馏是更合理的后续方向。

### 9.3 Benchmark 自动化

当前工程改动已经具备实验价值，但还缺：

- clean benchmark 自动回归
- corruption benchmark 自动回归
- 显存 / 延迟 profile 自动采集

没有这些自动化，后续很容易出现“感觉更稳了，但无法定量证明”的情况。

## 10. 建议的下一步实验顺序

建议按以下顺序执行，而不是同时铺开：

1. 在目标 Docker 环境完成镜像构建
2. 用 5-view 和 10-view 样本验证单卡 12GB 推理是否稳定
3. 记录 `AMP + OOM fallback + anchorlocal + GO early stop` 的延迟与显存收益
4. 跑 clean benchmark，确认没有明显回归
5. 跑 robust fine-tune，比较 clean / degraded 两套测试结果
6. 只有当推理资源目标仍不满足时，再进入 student / distillation 路线

## 11. 结论

本轮工作最重要的成果，不是单点优化，而是把“运行时稳健性”和“训练时稳健性”变成了可配置、可插拔、可继续实验的工程底座。

换句话说，本轮不是最终答案，而是后续研究和工程迭代的起点。  
它已经完成了最关键的第一步：把问题从“只能靠人工试错”转成“可以系统评估和继续优化”的状态。
