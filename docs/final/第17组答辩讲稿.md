## 第 1 页：封面

各位老师好，我们是第 17 组。我们的项目名称是 Better-MV-DUSt3R，一个基于 MV-DUSt3R 的多视图三维重建平台。

后面我会按项目定位、技术路线、核心实现、测试结果和总结分工来介绍。

## 第 2 页：课程任务与项目定位

这一页说明项目怎样对应课程要求。首先，项目使用 Python 3.12、CUDA 12.4 和 PyTorch 2.4.1，满足 Python 和 GPU 实践要求。其次，系统实现了从图片到模型的完整流程：多图或视频输入，经过质量评分、推理、全局优化，最后输出点云或 GLB。

在参考与创新方面，我们基于 DUSt3R/MV-DUSt3R，不把重点放在从零重写主干模型上，而是放在工程优化上，着重完成面向课程验收的工程优化、系统集成、测试验证和复现整理。项目最终交付包括仓库代码、Demo、CLI、图表、报告和部署脚本，保证软件实现和报告口径一致。

## 第 3 页：项目推进闭环

从开题到期末，我们先完成需求分析，明确课程任务、输入形式和验收指标；之后完成 Demo、CLI 和 runtime profile 的接入；中期阶段已经实现环境、权重、基础推理和初步优化。

期末阶段重点补齐闭环，包括 anchorlocal 视图配对、AMP 和 OOM 回退、全局优化早停、功能测试、性能测试、鲁棒性测试、消融实验和部署复现材料。也就是说，本项目最终不是只做到“能跑一次”，而是做到可运行、可测试、可解释、可复现。

## 第 4 页：技术路线选择

这一页比较几类三维重建路线，说明我们选择MV-DUSt3R的原因。传统 SfM/MVS 是经典几何管线，解释性强，但依赖特征匹配和多阶段优化，工程流程较重。NeRF 的视角合成效果好，但训练和采样成本较高，如果要导出网格或 GLB，还需要额外处理。

相比之下，DUSt3R/MV-DUSt3R 则较为适合我们的课程项目。它属于学习式几何预测，更贴近多图直接重建，同时保留全局对齐环节，方便我们做工程优化和结果验证。所以本项目选择 MV-DUSt3R 作为基础路线，在它之上做运行时、显存、配对和测试方面的优化。

## 第 5 页：技术路线总览

系统的整体流程可以概括为六步：输入、质量评分、视图配对、模型推理、全局优化和 GLB 输出。

输入阶段接收多图或视频帧；质量评分阶段判断图片清晰度、曝光和对比度；视图配对阶段决定哪些图片之间需要建立 pair；模型推理阶段调用 MV-DUSt3R 进行成对预测；全局优化阶段把局部预测对齐成统一场景；最后导出 GLB 供展示和验收。

## 第 6 页：系统架构

系统架构分为四层。第一层是交互层，使用 Gradio Demo 支持多图或视频上传，并提供结果预览。第二层是运行时层，包括 runtime profile、质量评分和 scene graph policy，负责统一参数和策略。

第三层是推理优化层，核心是 MV-DUSt3R 的成对预测，同时加入 AMP 和 OOM retry，降低显存压力。第四层是输出验证层，包括点云、GLB、日志、指标和部署脚本。

这里要强调，Demo 和 CLI 不是两套割裂流程。Demo 用于现场展示，CLI 用于批量测试和复现，但它们共享同一套运行时策略和输出口径。

## 第 7 页：输入质量评分与轻量预处理

多视图重建对输入质量很敏感。模糊会导致清晰度下降，低光照会让纹理变弱，过曝或欠曝会造成局部信息丢失，重复视角还会增加无效 pair。

为了解决这个问题，我们加入 quality_score，从清晰度、对比度和曝光裁剪等方面评价输入质量。同时，lite_robust_v1 中包含轻量预处理，并结合 adaptive threshold 做质量自适应置信度阈值。

这一部分对应课程中“图片整理、剔除模糊或过曝素材”的要求。我们的处理不是只靠人工筛选，而是把质量评估接入运行流程。

## 第 8 页：视图配对优化 anchorlocal

视图配对是影响性能的关键环节。如果使用 complete graph，所有图片两两配对，pair 数会随图片数量二次增长。比如 24 张图大约有 276 个 pair，推理时间和显存都会明显增加。

anchorlocal 的思路是使用高质量 anchor 加局部相邻边。高质量 anchor 用于保留全局参照，局部相邻边用于保留视角连续性。这样可以减少冗余 pair，同时尽量不破坏整体结构。

后面的性能测试中，耗时和显存下降，很大一部分就来自 pair 数减少和推理规模下降。

## 第 9 页：Runtime Profile 统一运行策略

这一页介绍 lite_robust_v1。原始 default 方案中，AMP、pair_batch_size、scene graph policy、预处理、质量自适应和全局优化参数都需要分别配置，现场演示和批量测试容易出现参数不一致。

lite_robust_v1 把这些常用策略统一成默认运行方案：AMP 默认开启，pair_batch_size 设置为 4 并配合 OOM retry，scene_graph_policy 支持 auto 或 anchorlocal，预处理使用轻量稳健配置，quality_adaptive 开启，全局优化使用早停参数。

这样 Demo 和 CLI 都可以使用同一套参数，减少复现风险。对答辩来说，它的价值是让演示、测试和报告结果都基于同一口径。

## 第 10 页：低显存推理

低显存推理主要依靠 AMP 和 OOM 自动回退。系统优先使用 batch=4，以保证吞吐；如果发生 CUDA OOM，就释放显存并自动降级到 batch=2；如果仍然失败，再降级到 batch=1，作为最后保底方案。

这个设计的目标是提高完成率。现场演示或者普通 GPU 环境中，最怕的是程序因为 OOM 直接中断。OOM retry 虽然可能牺牲一点速度，但能让流程尽量完成。

从测试数据看，24 图场景峰值显存从 13.6GB 降到 7.9GB；36 图场景从 18.9GB 降到 9.6GB。这说明优化后硬件门槛明显降低。

## 第 11 页：全局优化与早停

全局优化用于把成对预测结果对齐成统一三维场景，涉及 MST/PnP 初始化和全局比对循环。传统固定迭代方式的问题是：即使 loss 改善已经很小，系统仍可能继续迭代，造成时间浪费。

我们加入 min_iter、patience 等参数。系统先保证最小迭代次数，然后定期检查 loss 改善幅度。如果改善不足并持续达到 patience，就触发早停。

同时用 last_alignment_iterations 记录本次全局优化实际运行了多少轮。这样测试结果不只有最终模型，也有过程指标，更便于解释和复现。

## 第 12 页：稳健训练与数据扰动

这一页说明低质量输入问题在训练侧的设计。RGB corruption 用于模拟模糊、低光照和压缩等退化；corruption metadata 把扰动信息写入 sample 级元数据；geometry_loss_weight 对几何噪声样本下调 GT geometry loss 权重。

这里需要说明边界：我们不可能只通过这部分训练就达到行业 SOTA，这是不现实的。它的作用是把低质量输入问题扩展到训练稳健性设计中，并在代码和脚本层面留下证据，例如最下方的文件。

## 第 13 页：测试数据组与测试方法

这一页是测试部分的开始。我们设计了四组测试数据，每组 24 张图像。

clean-turntable 是干净转台场景，用作基础功能和精度基线；desk-scene 是桌面遮挡场景，用于测试遮挡情况下系统是否稳定；low-light 是低光照输入，用于测试光照退化；mixed-noise 是混合噪声输入，用于测试多种退化叠加时系统能否输出结果。

测试方法是：四组数据使用统一运行策略 lite_robust_v1，使用相同 CLI 或 Demo 参数执行。每组运行后，从日志、指标文件和输出结果中记录成功率、平均耗时、重投影误差、峰值显存和导出可读性。

这里最重要的是控制变量：数据组不同，但运行参数、统计口径和输出检查方式保持一致，这样结果才有可比性。

## 第 14 页：成功率与精度指标

这一页展示实验结果一，重点是成功率和重投影误差。

成功率表示系统成功完成重建并生成可检查输出的比例。这里的成功不是只看程序没有报错，还要看 GLB、日志和截图是否能用于展示和复查。它反映系统在不同输入质量下的稳定性。

重投影误差表示三维结果投影回二维图像后，与原图观测之间的像素偏差。误差越小，说明相机位姿和几何对齐越稳定。

结果上，clean-turntable 成功率 96%，重投影误差 0.42px，说明干净输入下效果最好；desk-scene 成功率 92%，误差 0.53px，说明遮挡会带来影响但仍可控；low-light 成功率 86%，误差 0.66px；mixed-noise 成功率 80%，误差 0.79px。

可以看到，输入质量越差，成功率下降、误差上升，这是符合预期的。但系统仍然能输出可展示模型，说明质量评分、轻量预处理和稳健运行策略发挥了作用。

## 第 15 页：耗时与显存指标

这一页展示性能测试。这里主要看两个指标：端到端耗时和峰值显存。

端到端耗时指从开始执行重建命令，到 scene.glb、日志和指标输出完成为止的总时间。24 图场景中，耗时从 495s 降到 211s，说明 anchorlocal 减少 pair 数、全局优化早停减少无效迭代、runtime profile 减少了人工调参成本。

峰值显存指运行过程中 GPU 显存的最高占用。24 图场景从 13.6GB 降到 7.9GB；36 图场景从 18.9GB 降到 9.6GB。这个指标说明系统对硬件的要求降低了，普通 GPU 更容易完成完整流程。

所以性能优化的价值不是只追求跑得快，而是让系统更稳定、更容易。

## 第 16 页：消融实验

消融实验用于判断每个改动分别有什么贡献。测试方法是以默认流程为对照，分别观察 anchorlocal、lite_robust_v1、AMP、OOM retry、GO early-stop 和 quality adaptive 对结果的影响。

从结果解释看，anchorlocal 对规模扩展贡献最大，因为它直接减少 pair 数；lite_robust_v1 是默认主方案，把多项优化统一成一个入口；AMP 降低显存并提高吞吐；OOM retry 提供失败恢复能力；GO early-stop 减少无效迭代；quality adaptive 提高低质量输入下的稳定性。

主结论是：anchorlocal 和 lite_robust_v1 是核心方案，其他机制共同保证系统稳定性。

## 第 17 页：现场演示与复现路径

项目提供 Demo 和 CLI 双入口。Demo 入口适合现场上传图片并预览结果，命令中通过 runtime_profile 使用统一策略。CLI 入口适合批量测试和复现实验，可以指定 scene_graph_policy、pair_batch_size 和 oom_retry 等参数。

输出包括 scene.glb、运行日志、指标和截图。环境包括 Python 3.12、CUDA 12.4、PyTorch 2.4.1，也提供 Docker 一键部署方案。
