# 答辩模拟 Q&A

本文预测答辩中可能被追问的问题。重点放在创新点、测试数据获取、评估指标设定，以及项目边界说明。

## 一、创新点相关

### Q1：你们的创新点是什么？是不是重新设计了 MV-DUSt3R 模型？

不是重新设计主干模型。我们的创新点是把 MV-DUSt3R 改造成适合课程验收的工程优化平台，主要包括五点：第一，统一 runtime profile，让 Demo 和 CLI 使用同一套运行策略；第二，加入输入质量评分和质量自适应阈值；第三，用 anchorlocal 减少多视图 pair 爆炸；第四，通过 AMP 和 OOM retry 降低显存门槛；第五，加入全局优化早停和运行日志记录，方便测试和复现。

可以概括为：我们做的是模型基础上的工程创新和复现实验闭环，不是论文级新网络结构。

### Q2：如果没有改网络结构，为什么还能称为创新？

课程项目不一定要求提出新网络。我们面对的是工程使用中的真实问题：低显存设备跑不动、多图 pair 数增长太快、低质量输入难解释、Demo 和 CLI 参数不一致、实验结果难复查。

我们的改动把这些问题变成可配置、可记录、可测试的模块。例如 anchorlocal 直接降低配对规模，OOM retry 提高完成率，质量评分把输入质量转为数值，全局优化早停记录迭代过程。这些都是面向系统落地的创新。

### Q3：你们和原始 MV-DUSt3R 相比，最核心的差别是什么？

原始项目更偏模型训练和推理能力。本项目更偏课程工程平台：保留原始训练、推理和 Demo 思路，同时补充低显存推理、质量自适应重建、anchorlocal 视图策略、稳健训练脚本、Docker/命令行复现材料和测试指标。

一句话说，原始 MV-DUSt3R 解决“模型怎么做多视图重建”，我们的项目解决“在课程设备和答辩场景下，怎样稳定运行、解释结果、复现测试”。

### Q4：anchorlocal 为什么算创新？不就是少算一些 pair 吗？

不是简单少算。complete graph 会把所有图像两两配对，n 张图约有 n(n-1)/2 个 pair，24 张图约 276 个 pair。anchorlocal 的思路是选择高质量 anchor 保留全局参照，同时保留局部相邻边维持视角连续性。

所以它不是随机删边，而是在全局参照和局部连续之间折中。它直接服务于多图场景下的耗时和显存控制。

### Q5：lite_robust_v1 的意义是什么？为什么不让用户自己调参数？

如果每次都手动调 AMP、batch size、scene graph、预处理、质量阈值和早停参数，演示和测试很容易口径不一致。lite_robust_v1 把这些配置收敛为一个默认方案，让 Demo、CLI、报告和复现实验使用同一套策略。

它的意义不是参数本身多复杂，而是降低复现风险，让老师或同学能按同一命令得到同类结果。

### Q6：全局优化早停会不会牺牲精度？

早停不是一开始就停，而是先保证最小迭代次数，再按 check_every 定期检查 loss 改善幅度。如果连续多次改善都小于 rel_tol，才根据 patience 触发停止。

这样做的目标是减少无效迭代，而不是跳过必要优化。我们还记录 last_alignment_iterations，用于说明每次运行实际优化了多少轮。

### Q7：质量评分会不会太简单？

质量评分确实不是复杂的图像质量评价模型，但它适合本项目。我们需要的是轻量、可解释、能进入运行流程的指标。清晰度、对比度和曝光裁剪能对应模糊、低光照、过曝/欠曝这几类常见问题。

如果继续做研究型扩展，可以引入更复杂的图像质量评价模型；但课程项目中，简单可解释的质量评分更适合答辩和复现。

## 二、测试数据获取相关

### Q8：测试数据从哪里来？

项目有两类数据口径。第一类是上游训练和评估可使用的数据来源，包括 ScanNet、ScanNet++、HM3D、Gibson 和 MP3D，这些在项目 README 和 data 说明中保留。第二类是本次答辩使用的课程复现实验数据组，包括 clean-turntable、desk-scene、low-light、mixed-noise 四组输入，每组 24 张图像。

答辩中主要讲第二类，因为它直接对应 PPT 中的测试结果。

### Q9：四组测试数据分别怎么设计？

clean-turntable 是干净转台场景，用作基础功能和精度基线；desk-scene 是桌面遮挡场景，用于观察遮挡和普通室内纹理下的稳定性；low-light 是低光照输入，用于测试光照退化；mixed-noise 是混合噪声输入，用于测试多种退化叠加时系统能否输出结果。

四组的目的不是覆盖所有真实世界场景，而是覆盖课程验收最关心的几类输入：理想输入、遮挡输入、低光照输入和复杂退化输入。

### Q10：为什么每组选择 24 张图像？

24 张图像能覆盖一个相对完整的多视角输入，同时又不会让课程设备无法承受。它也能体现 complete graph 的 pair 增长问题：24 张图完整图约 276 个 pair，足以观察 anchorlocal 对配对规模、耗时和显存的影响。

如果图像太少，看不出视图策略差异；如果图像太多，答辩设备和运行时间压力会过大。

### Q11：测试数据是公开数据集吗？

答辩 PPT 中的四组数据主要是课程复现实验数据，不应表述为公开 benchmark。项目本身保留了上游数据集说明，但本次结果的重点是固定环境、固定权重、统一运行配置下的对比趋势。

如果老师追问，可以明确说明：我们不把这些结果包装成公开排行榜，而是用于课程验收和工程策略验证。

### Q12：low-light 和 mixed-noise 是怎么得到的？

可以按两层回答。实验输入层面，它们代表低光照和混合退化场景，用于测试系统在非理想输入下是否仍能输出可检查结果。训练设计层面，项目还提供 RGB corruption 和 corruption metadata，用于模拟模糊、低光照、压缩等扰动，并记录扰动信息。

也就是说，我们既有面向答辩测试的数据组，也有代码层面的扰动设计，用来说明低质量输入问题不是只在 PPT 中口头描述。

### Q13：如何保证不同数据组之间可比？

我们控制运行条件：固定权重 `checkpoints/best.pth`，固定运行策略 `lite_robust_v1`，使用相同 Demo 或 CLI 参数，记录同一组指标。这样输入数据是主要变量，统计口径保持一致。

这种设计不能代表大规模统计结论，但能支持课程复现实验中的相对比较。

### Q14：如果老师问“数据量太小怎么办”？

可以承认这是项目不足。每组 24 张图适合课程答辩和工程验证，但不足以支撑行业级泛化结论。后续可以扩展更多场景、更多光照条件、更多物体类型，并引入公开 benchmark 的标准划分。

同时强调：本项目当前目标是验证工程策略是否有效，而不是发布完整 benchmark。

## 三、评估指标设定相关

### Q15：为什么选择成功率、耗时、重投影误差、峰值显存和导出可读性这些指标？

这些指标分别对应课程验收中的不同问题。成功率回答“能不能稳定跑完”；平均耗时回答“使用成本是否可接受”；重投影误差回答“几何对齐是否合理”；峰值显存回答“普通 GPU 能不能运行”；导出可读性回答“结果能不能展示和复查”。

它们覆盖了功能、性能、几何质量、硬件资源和复现展示五个维度。

### Q16：成功率具体怎么定义？

成功率是成功完成重建并生成可检查输出的比例。这里的成功不只是程序没有崩溃，还包括输出 GLB、日志、指标和截图等材料能用于展示或复查。

如果某次运行虽然命令结束了，但没有可打开的结果文件，不能算完整成功。

### Q17：为什么使用重投影误差作为精度指标？

三维重建最终要满足多视图几何一致性。重投影误差把三维结果投影回原图，计算与二维观测之间的偏差。误差越小，说明相机位姿和三维结构越一致。

它的优点是与多视图几何直接相关，也便于解释；缺点是它不等同于完整三维真值误差，所以我们没有把它说成唯一精度标准。

### Q18：为什么没有使用 Chamfer Distance 或 F-score？

这些指标通常需要可靠的三维真值模型或高质量参考点云。本项目的课程复现实验重点是多图输入到可展示输出，不是完整公开三维 benchmark，因此优先选择更容易在当前环境中记录的指标。

后续如果扩展到标准数据集和真值模型，可以加入 Chamfer Distance、F-score、法线一致性等更严格的几何指标。

### Q19：峰值显存怎么记录？为什么重要？

峰值显存是运行过程中 GPU 显存占用的最高值，可以通过运行日志或 GPU 监控工具记录。它重要是因为三维重建很容易受硬件限制，尤其多图输入会显著增加 pair 数和中间张量占用。

项目中 24 图场景显存从 13.6GB 降到 7.9GB，36 图场景从 18.9GB 降到 9.6GB，说明 AMP、anchorlocal 和 OOM 回退降低了硬件门槛。

### Q20：平均耗时从什么时候开始算，到什么时候结束？

从开始执行重建命令或启动一次完整推理流程开始，到 scene.glb、日志和指标输出完成为止。这个定义是端到端耗时，包含实际用户等待的主要过程。

如果只统计模型前向时间，会低估用户真实使用成本，所以我们选择端到端耗时。

### Q21：导出可读性是不是主观指标？

它有一定人工检查成分，但在课程验收中很实用。我们检查 GLB 是否能正常打开，点云或预览是否能辨认主要结构，日志和指标是否存在。它用于补充纯数值指标，避免出现“数值有了但结果无法展示”的情况。

更严格的后续方案可以把导出可读性细化为自动文件检查、点数统计、边界范围检查和查看器加载测试。

### Q22：为什么低质量输入下成功率下降仍然说策略有效？

低质量输入本身会破坏几何和纹理信息，成功率下降是合理现象。策略有效不是指完全消除下降，而是指系统没有直接崩溃，仍能输出可检查模型，并且下降趋势能被质量评分、噪声类型和重投影误差解释。

例如 clean-turntable 成功率最高，mixed-noise 最低，这和输入难度一致，说明指标趋势是合理的。

### Q23：消融实验怎么设计？

以默认方案 `lite_robust_v1` 为主方案，再分别观察关键机制的影响：关闭或替换 anchorlocal、AMP、OOM retry、GO early-stop、quality adaptive 等。比较它们对耗时、显存、成功率、配对规模和输出稳定性的影响。

消融实验的核心是回答“哪项优化解决了哪个问题”，而不是只给一个总结果。

### Q24：你们怎么证明 anchorlocal 对耗时有贡献？

从机制上，anchorlocal 减少 pair 数，推理规模下降；从实验上，24 图完整图约 276 pair，anchorlocal 避免了完整两两配对，耗时和显存都下降。两者结合说明它是性能提升的重要来源。

答辩时可以说：这是一个“公式可解释 + 实验可观察”的贡献。

### Q25：质量评分和最终结果之间是什么关系？

质量评分不是直接预测重建质量，而是解释输入风险。低质量图像更可能导致点云稀疏、误差上升或输出不稳定。通过记录 quality_score，我们可以把低光照、模糊、过曝等问题提前量化，便于解释不同数据组的结果差异。

## 四、项目边界与不足

### Q26：你们项目有没有达到 SOTA？

不这样宣称。我们的目标不是刷新公开榜单，而是完成课程项目中的工程优化、系统集成和复现实验。我们基于 MV-DUSt3R，重点解决低显存、输入质量、视图配对、运行配置和输出验证问题。

如果继续做研究，可以扩大数据集、加入标准真值指标、与更多方法进行对比。

### Q27：你们的训练改动是否充分验证？

稳健训练部分提供了 corruption-aware sampling、RGB/geometry corruption 和 geometry_loss_weight 设计，但当前答辩重点是工程运行和课程复现实验。我们不夸大训练部分结论，只说明它为低质量输入问题提供了训练侧扩展方向。

### Q28：为什么不用更复杂的图像质量评价或更智能的视图选择？

因为课程项目优先考虑可解释、可实现、可复现。复杂模型可能效果更强，但会引入额外依赖、训练成本和解释成本。当前方案用清晰度、对比度、曝光裁剪和 anchorlocal 已经能解释主要实验现象。

后续可以把这部分升级为学习式质量评价或基于特征覆盖度的视图选择。

### Q29：Demo 和 CLI 结果会不会不一致？

我们尽量通过 runtime profile 统一运行策略。Demo 适合交互展示，CLI 适合批量测试；两者共享同一类参数思想，包括 AMP、预处理、质量自适应等。CLI 暴露的控制项更多，所以用于实验统计更合适。

### Q30：如果现场演示失败，如何解释项目仍然可复现？

现场演示受 GPU、依赖、端口、显存和文件路径影响。我们准备了 CLI 命令、运行日志、输出 GLB、指标文件、截图、Docker 和 run.ps1。即使现场网络或设备异常，也可以通过这些归档材料复查项目流程。

## 五、答辩时可直接使用的短回答

### 创新点一句话

我们的创新点不是重写网络，而是把 MV-DUSt3R 工程化为低显存、质量自适应、可复现的课程三维重建平台。

### 数据来源一句话

训练和上游说明保留 ScanNet、ScanNet++、HM3D、Gibson、MP3D 等数据口径；答辩测试使用四组课程复现实验输入，每组 24 张图，覆盖干净、遮挡、低光照和混合噪声。

### 指标设置一句话

指标围绕课程验收设计：成功率看稳定性，耗时看使用成本，重投影误差看几何一致性，峰值显存看硬件门槛，导出可读性看展示和复查。

### 不足一句话

目前数据规模和几何真值指标还不够完整，后续可以扩展公开 benchmark、Chamfer Distance、F-score 和更多真实场景。
